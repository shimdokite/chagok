# 차곡 1일차 구현 지시서 Implementation Plan

> Codex 실행 지침: 이 문서를 처음부터 읽고 실제 작업 저장소와 AGENTS.md를 확인한 다음 **1일차만 구현**한다. 실행 계획 스킬이 있으면 `superpowers:executing-plans`로 순서대로 진행한다. 새 설계를 다시 제안하거나 전체 MVP를 하루에 구현하지 않는다. 현재 요청은 아래 명세의 구현을 허용한다. 사용자 변경은 보존하고, 필요한 계정·기기 정보만 질문하며 나머지 작업을 진행한다.

**Goal:** 승인된 차곡 디자인의 네이티브 로그인·홈과 Next.js 웹뷰 연결을 만들고, 실제 tRPC 서버 통신과 양방향 브릿지를 검증하며 첫 측정 기준선을 남긴다.

**Architecture:** Expo·React Native 앱은 네이티브 화면과 이동을 담당한다. Next.js는 신청 웹뷰와 Node.js 런타임의 tRPC API를 제공한다. 오늘 API는 연결 확인만 제공하며, 실제 인증·PostgreSQL 저장·한도 변경은 이후 일정에서 구현한다.

**Tech Stack:** TypeScript, React Native, Expo Development Build, Expo Router, react-native-webview, Next.js App Router, tRPC, Zod. 이후 TanStack Query, Tailwind CSS, shadcn/ui, PostgreSQL, Prisma를 필요한 순서로 추가한다. 별도 NestJS 서버는 이번 기본안에 포함하지 않는다.

**Spec:** 이 문서의 MVP·시각 기준·인터페이스가 독립 실행 가능한 명세다. 함께 제공된 `chagok-mobile-reference.png`, `chagok-admin-reference.png`, `chagok-prototype.html`을 참고한다. 이 문서를 저장소의 `docs/plans/day-01.md`로 보관하고 실제 경로·진행 상태는 별도 기록한다.

**공통 제약:** 하루 5~6시간, 오늘은 1일차, 가상 데이터 사용, 실측 원본 보존, 원 단위 정수, 실제 송금 없음, 과금 기능 신설 없음. 완료하지 않은 작업과 보지 못한 실기기를 완료로 표시하지 않는다.

**검토할 실패 조건:** 서버에 연결되지 않음, 웹뷰 로딩 실패·재로드, 잘못된 메시지, 중복·지연 응답, 화면을 닫은 뒤 남는 타이머. 각각 아래 구현·검증 항목에서 다룬다.

## 1. 배경과 목표

### 프로젝트 배경

도연님은 React·Next.js와 Node.js 개발 경험이 있으며 React Native는 처음이다. 캐노피 Frontend Developer Junior 지원을 위해 10일간 하루 5~6시간씩 개발한다. React Native·Next.js 웹뷰·네이티브 브릿지·타입 안전한 API를 직접 연결하고, 구현과 최적화 결과를 설명할 수 있는 포트폴리오를 만드는 것이 목적이다. 서류 합격을 보장하는 프로젝트라고 표현하지 않는다.

차곡은 직원이 복지 한도를 확인하고 영수증을 첨부해 복지비를 신청하면 담당자가 승인·반려하는 서비스다. 급여 선지급이나 실제 금융 송금 서비스가 아니다. 기존의 다른 프로젝트인 ‘오늘 번 돈’ 지시서와 이 문서가 충돌하면 현재 차곡 명세를 적용한다.

## 2. MVP 범위

### 최종 MVP

| 기능 | 최종 범위 |
| --- | --- |
| 구글 로그인 | 실제 구글 인증, 서버 검증·사용자 등록/조회, 앱 세션 복원·로그아웃·만료 처리 |
| 데모 접근 | 검토자용 가상 직원·담당자, 실제 계정과 구분된 데이터·권한 |
| 회사별 복지 | 가상 회사 2곳의 지원 항목·한도 설정을 서버에서 적용 |
| 직원 홈 | 총 한도, 접수·승인 금액, 잔여 한도, 지원 항목, 최근 내역 |
| 신청 | 항목·사용일·금액·내용·영수증, 서버 검증·중복 방지 |
| 영수증 | 네이티브 사진 촬영·선택 → 웹뷰 미리보기 → 실제 파일 저장 |
| 신청 내역 | 접수·승인·반려 상태, 상세·영수증·반려 사유 |
| 담당자 웹 | 회사 소속 신청만 조회·검토·승인·반려 |
| 측정·최적화 | 기준선, 실제 병목 분석, 변경 전후 원본, 정확성·사용성 회귀 확인 |

최종 상태 식별자는 `SUBMITTED`, `APPROVED`, `REJECTED`로 통일한다. 시안의 `pending`, `approved`, `rejected`는 각각 이 상태에 매핑한다. 미제출은 DB 상태가 아닌 클라이언트 작성 상태다.

한도는 원 단위 정수로 관리한다. `사용 가능 한도 = 월 총한도 - SUBMITTED 합계 - APPROVED 합계`다. 승인 시 재차 차감하지 않고, 반려 시 해당 접수 금액을 한도에 복원한다. 실제 처리 권한·금액·잔액은 서버가 판단한다. 이는 이후 일정의 업무 규칙이며 오늘은 가상 표시만 한다.

### 오늘 구현할 것

- [ ] 기존 저장소를 확인하고 실제 경로·명령·기존 생성/과금 흐름의 존재 여부를 기록한다.
- [ ] 비어 있는 저장소라면 mobile·web·공유 패키지를 최소 구조로 준비한다. 기존 구조가 있으면 이를 따른다.
- [ ] Expo Development Build를 우선 OS 한 곳에서 실행한다. 실제 기기 여부·모델·OS·실행 방식은 기록한다.
- [ ] 승인 시안의 네이티브 로그인 화면과 홈을 구현한다. ‘데모로 둘러보기’로 홈에 들어간다.
- [ ] 구글 로그인 버튼은 비활성 상태와 ‘로그인 준비 중’ 안내를 둔다. 구글 버튼으로 인증 없이 홈에 들어가는 시안 동작을 실제 로그인으로 복제하지 않는다.
- [ ] 홈의 한도·지원 항목·최근 신청을 고정된 가상 fixture로 표시하고 ‘데모 데이터’임을 알린다.
- [ ] `health.check` tRPC query를 실제 Next.js 서버에서 제공하고 앱에서 호출한다. 서버 중단 시 오류·재시도를 확인한다.
- [ ] 홈의 신청 버튼에서 실제 Next.js `/apply`를 웹뷰로 연다. 웹 화면은 시안의 헤더·입력 영역 배치를 가진 비활성 폼이다. 금액 입력·첨부·제출은 준비 중 상태로 두고 데이터 변경을 하지 않는다.
- [ ] 웹→앱 `WEB_READY`, 앱→웹 `PING`, 웹→앱 `PONG`, 웹→앱 `CLOSE_WEBVIEW`를 연결한다.
- [ ] 개발 전용 계측 도구에서 20회 순차 왕복 측정·결과 내보내기를 제공한다. 일반 제품 화면에 기술 로그를 상시 표시하지 않는다.
- [ ] 로딩·오류·다시 시도·닫기를 구현하고, 실제 검증 결과·기준선·학습 기록을 남긴다.

하단 ‘신청 내역’·‘복지 안내’와 최근 신청 행은 오늘 완성하지 않는다. 버튼을 연결한다면 ‘준비 중’ 안내까지만 제공하고, 잘못된 라우트·빈 화면·완료된 것처럼 보이는 동작을 만들지 않는다.

### 파이프라인과 계약

오늘의 실행 단계는 아래뿐이다. 기존 CI·생성·결제 파이프라인의 교체를 뜻하지 않는다.

| 단계 | 입력 → 출력 | 상태 변경 |
| --- | --- | --- |
| 앱 시작 | 설정 → 로그인 화면 → 데모 홈 | 화면 상태만 |
| 서버 확인 | `health.check` → `{ status: 'ok', service: 'chagok' }` | 없음 |
| 신청 화면 열기 | 홈 CTA → 앱 내 `/apply` WebView | 한도·크레딧 변경 없음 |
| 웹 준비 | 수신 함수 등록 → `WEB_READY` | 브릿지 준비 상태만 |
| 왕복 측정 | `PING(requestId)` → `PONG(requestId)` | 측정 메모리만 |
| 화면 닫기 | `CLOSE_WEBVIEW` → 타이머 정리 → 홈 | 금액 변경 없음 |

`health.check`는 public query이며 오늘은 상태 값만 반환한다. 설치한 tRPC 버전의 공식 adapter로 `/api/trpc`에 연결하고 앱에서 `client.health.check.query()`를 호출한다. 실패를 가짜 성공 값으로 대체하지 않는다. DB·토큰·내부 환경변수는 응답에 포함하지 않는다.

브릿지 메시지는 다음 계약을 따른다. `payload`는 오늘 빈 객체만 허용한다.

```ts
type BridgeBase = { channel: 'chagok.bridge'; version: 1 };
type BridgeMessage = BridgeBase & (
  | { type: 'WEB_READY'; payload: Record<string, never> }
  | { type: 'PING'; requestId: string; payload: Record<string, never> }
  | { type: 'PONG'; requestId: string; payload: Record<string, never> }
  | { type: 'CLOSE_WEBVIEW'; payload: Record<string, never> }
);
```

- `requestId`는 비어 있지 않은 최대 128자 문자열이다. 이 값은 오늘 측정 요청을 구분하는 식별자이며 인증·권한을 대신하지 않는다.
- 웹→앱은 설치한 react-native-webview의 `window.ReactNativeWebView.postMessage(JSON.stringify(message))`와 `onMessage`를 사용한다.
- 앱→웹은 설치 버전의 지원 API를 확인한 뒤 웹 측에 등록한 `window.__CHAGOK_BRIDGE__.receive(message: unknown): void`로 전달한다. 기본안은 `injectJavaScript`에서 직렬화된 JSON을 넘기는 방식이다. 직접 문자열 삽입·임의 코드 실행은 금지하고 종료 반환값·수신 등록 순서·플랫폼 차이를 확인한다.
- 수신 함수를 등록한 다음 웹이 `WEB_READY`를 보낸다. 앱은 준비 전 PING을 보내지 않는다. 재로드 시 pending 측정을 취소하고 ready를 다시 기다린다.
- 웹이 단독 브라우저에서 열리면 브릿지 객체가 없어도 화면을 표시한다. ‘앱에서 이용할 수 있어요’ 안내를 두고 준비 메시지 전송을 생략한다.
- 양쪽에서 JSON·channel·version·type·payload·requestId를 런타임 검증한다. 잘못된 메시지는 동작을 유발하지 않고 개발 로그에서 이유만 확인한다.
- 허용한 웹 origin과 `/apply` 경로만 로드한다. 외부 이동·새 창·알 수 없는 메시지가 네이티브 동작을 실행하지 못하도록 한다. origin 검사는 로그인 인증을 대체하지 않는다.
- 타이머·in-flight Map·리스너·웹 전역 수신 함수는 닫기·재로드·unmount 시 정리한다. 중복 PONG이나 시간 초과 뒤 응답은 성공을 추가하지 않는다.
- 오늘은 `FORM_READY`를 구현하지 않는다. `WEB_READY`는 브릿지 연결 준비이며, 실제 인증·정책·입력 준비가 완료됐다는 신호가 아니다.

## 4. Acceptance Criteria

각 문장은 예/아니오로 판정한다. ‘예’는 실행 근거가 있을 때만 선택한다. 조건부 항목은 먼저 적용 여부와 근거를 기록하며, 미존재를 통과로 위장하지 않는다. 확인할 수 없으면 ‘아니오·수동 확인 필요’로 남긴다.

- [ ] AC01 실제 저장소 경로·AGENTS.md·실행 명령·확정된 변경 파일이 기록되어 있다.
- [ ] AC02 우선 OS의 Development Build에서 앱이 실행되고 기기·OS·실행 방식이 기록되어 있다.
- [ ] AC03 시안의 색상·배치·타이포를 따르는 네이티브 로그인·홈이 보이며 가짜 기기 프레임이 없다.
- [ ] AC04 ‘데모로 둘러보기’로 홈에 진입하고 실제 구글 로그인 완료로 표시하지 않는다.
- [ ] AC05 홈이 총 100,000원·접수 및 승인 35,000원·잔여 65,000원을 표시하고 반려 30,000원은 차감하지 않는다.
- [ ] AC06 모바일 앱이 실제 `health.check` API의 성공 응답을 확인하며 서버 중단 시 오류·재시도를 제공한다.

- [ ] AC08 WEB_READY 이전에는 PING 측정이 시작되지 않으며, 올바른 requestId의 PONG만 대응된다.
- [ ] AC09 malformed JSON·다른 channel·지원하지 않는 version·type·payload가 화면 이동·금액 변경을 유발하지 않는다.
- [ ] AC10 닫기·재로드·재진입 후 중복 리스너·남은 타이머로 성공 수가 중복 집계되지 않는다.
- [ ] AC11 신청 화면 열기·닫기·벤치마크·재시도 전후 데모 한도는 65,000원으로 유지되고 신청 레코드가 새로 저장되지 않는다.
- [ ] AC12 브릿지 20회 측정의 실제 원본·환경·성공/실패/시간 초과·중앙값·최소/최대가 남아 있다. 미실행이면 ‘아니오·미측정’이다.
- [ ] AC13 타입 검사·외부 입력/계측 테스트·웹 빌드의 실제 명령·종료 결과가 기록되어 있다.
- [ ] AC14 **기존 생성 플로우가 그대로 동작한다.** 실제 저장소에 기존 생성 플로우가 있으면 변경 전후 동일 절차를 확인한다. 없으면 ‘기존 생성 플로우 미존재·적용 제외’ 근거를 기록한다. 차곡의 새 신청 생성은 4일차 범위이며 오늘 완료로 표시하지 않는다.
- [ ] AC15 기존 승인 시안은 수정되지 않았으며 기존 가상 신청 → 접수 → 한도 갱신 → 승인·반려 흐름을 회귀 확인했거나 수동 확인 필요로 명시했다.
- [ ] AC16 크레딧 과금 경로가 존재하면 오늘 새 조회·웹뷰·계측 흐름에서 크레딧 잔액·차감 원장 변화가 0임을 확인했다. 경로가 없으면 미존재·적용 제외 근거를 기록했다.
- [ ] AC17 민감값이 코드·공개 env·URL·일반 로그·측정 원본에 포함되지 않는다.
- [ ] AC18 `docs/progress.md`, 오늘 측정·학습 기록, 다음 작업 시작점이 갱신되어 있다.

AC12를 채우기 위해 임의 값을 넣지 않는다. 기기 접근·빌드·측정이 막히면 나머지를 완료하고 미완료 항목·원인·필요 조치를 보고한다.

## 5. 테스트 체크리스트

### 자동 검증

실제 저장소의 명령 이름은 Codex가 탐색 후 확정한다. 신규 기본안은 `npm run typecheck`, `npm test`, `npm run build:web`, mobile workspace에서 `npx expo-doctor`다. 이 명령을 제공하려고 정상인 기존 스크립트·테스트 도구를 바꾸지 않는다. 최초 실행 결과와 수정 뒤 결과를 구분하고 실행하지 않은 명령은 통과로 표시하지 않는다.

| 대상 | 확인할 입력·상황 | 기대 결과 |
| --- | --- | --- |
| 브릿지 파싱 | 올바른 WEB_READY·PING·PONG·CLOSE_WEBVIEW | 계약에 맞게 파싱 |
| 브릿지 파싱 | 깨진 JSON·다른 channel·version 2·unknown type | 오류 반환, 네이티브 동작 없음 |
| 브릿지 파싱 | 빈/129자 requestId·잘못된 payload | 거부 |
| 요청 대응 | 다른 requestId·동일 PONG 2회 | 다른 요청 미완료, 동일 요청 성공 1회 |
| 시간 초과 | 3,000ms 응답 없음·시간 초과 뒤 PONG | timeout 1회, 뒤늦은 성공 추가 없음 |
| lifecycle | 웹뷰 닫기·재로드·컴포넌트 unmount | pending 취소·타이머 정리·ready 초기화 |

### 오늘의 측정 기록

- 대상: 같은 웹뷰 세션에서 RN→웹→RN PING/PONG 왕복 시간(ms).
- 조건: ready 이후 준비 왕복 3회를 별도 기록하고 본 측정 20회를 진행한다. 개발 빌드·웹 development/production 중 실제 모드를 적는다. 최종 실험은 이후 릴리스·웹 production 조건에서 별도 재확인한다.
- 성공 기준: 전송한 requestId에 대응하는 PONG이 3,000ms 이내 수신됨.
- 요약: 시도·성공·실패·timeout·취소, 성공 샘플 중앙값·최소·최대. 20회로 p95를 대표 성과로 강조하지 않는다.
- 원본 필드: experimentId, sessionId, sampleId, requestId, sentAtMonotonicMs, receivedAtMonotonicMs, durationMs, status, reason, device, OS, appBuild, webBuildMode, sourceRef, measuredAtKst.

- 실제 API 연결 확인 성공/시도도 기록할 수 있다. 성공률은 분자/분모와 함께 적고 운영 신뢰성으로 일반화하지 않는다.
- 추가 수치화 후보를 발견하면 사용자 경험·정확성과의 관련성, 지표 정의·측정 비용을 기록하고 오늘 범위 안에서만 추가한다. 큰 최적화는 후보로 남겨 이후 실험한다.

## 6. 주의사항

### 크레딧 과금 경로와 복지 한도의 구분

현재 차곡 시안에는 AI 생성·크레딧 지갑·크레딧 과금 기능이 없다. ‘크레딧 차감’을 복지 한도 차감과 같은 로직으로 임의 해석하지 않는다. 실행할 저장소가 달라 실제 과금 코드가 있다면 먼저 credit·billing·charge·generation·payment 등의 키워드와 생성 진입점·worker·webhook·ledger 호출을 확인하고 실제 경로를 `docs/repository-map.md`에 기록한다.

| 작업 | 오늘의 금액·크레딧 효과 | 이후 규칙 |
| --- | --- | --- |
| 홈·로그인 화면 표시, health 조회 | 복지 한도 변화 0, 크레딧 차감 0 | 동일 |
| 웹뷰 열기·닫기, bridge ping, 재시도 | 복지 한도 변화 0, 크레딧 차감 0 | 동일 |
| 영수증 선택·실패·제출 전 취소 | 오늘 미구현, 어떠한 차감도 없음 | 선택·업로드만으로 복지 한도를 차감하지 않음 |
| 신청 접수 | 오늘 저장·차감 없음 | 서버에서 한 번만 접수 금액을 예약 |
| 신청 승인 | 오늘 미구현 | 접수 단계에서 예약한 금액을 재차 차감하지 않음 |
| 신청 반려 | 오늘 미구현 | 서버에서 한 번만 복원 |
| 기존 유료 생성 | 발견된 경우 기존 경로 보존 | 기존 가격·차감·복원 계약 유지 |

기존 생성 경로가 발견돼도 이 작업을 이유로 가격·크레딧 단위·잔액 원장·차감 시점·결제 webhook·재시도·환불 규칙을 바꾸지 않는다. 기존 유료 흐름 검증은 승인된 테스트 환경에서 수행하고 실제 결제나 유료 생성 호출이 필요하면 먼저 비용과 검증 범위를 구체적으로 알린다. 과금 경로가 없으면 새로 만들지 않는다.

### 건드리지 말아야 할 것

- 승인된 원본 시안과 다른 프로젝트 파일, 기존 사용자 변경, 기존 인증·생성·과금·배포 설정.
- 운영 DB·실제 직원 정보·실제 영수증·운영용 OAuth 비밀값.
- 기존 저장소 전체 구조·lockfile을 불필요하게 재작성하거나 React 버전을 일괄 latest로 올리는 작업.
- 테스트를 통과시키기 위한 assertion 삭제, timeout 확대만으로 실패 숨기기, 기준선에 인위적 지연·중복 요청 추가.
- 실제 서버 통신을 fixture 응답으로 바꾼 뒤 연결 성공이라고 기록하는 작업.
- 승인되지 않은 앱 공개 출시·실제 송금·유료 서비스 구독·실결제.

### 구현·보안·운영 원칙

- 신규 코드의 작은 가역적 결정은 Codex가 판단하고 기록한다. 이미 합의한 MVP·스택을 다시 확인받느라 멈추지 않는다.
- 설치 버전별 공식 문서를 확인한다. Next.js·Expo·tRPC 예제를 서로 다른 메이저 버전에서 혼용하지 않는다.
- 모바일 RN UI는 네이티브 컴포넌트와 StyleSheet를 기본으로 한다. shadcn/ui·Tailwind는 웹 영역에 적용한다.
- 공개 환경변수에는 웹 origin·공개 client ID 등 공개 가능한 값만 둔다. 이후 client secret·DB URL·서명키는 서버 전용이다.
- 기기에서 localhost는 기기 자신이다. LAN 주소·시뮬레이터 host 매핑·허용 origin을 환경별로 기록한다. 공개 터널·유료 계정이 필수라고 단정하지 않는다.
- 로컬 개발 HTTP가 필요하면 해당 개발 설정에 한정한다. 전체 앱의 인증서 검증·HTTPS 정책을 끄지 않는다.
- HTTP 실패·권한 부재·미구현을 사용자에게 설명할 수 있는 상태로 표시한다. 제품 UI에 tRPC·bridge·database 같은 구현 설명을 상시 넣지 않는다.
- 로그·계측에는 토큰·개인정보를 넣지 않는다. requestId·상태·시간 등 필요한 최소 정보만 보존한다.
- Git commit이 가능한 저장소에서는 작은 논리 단위로 기록하고 사용자 변경을 섞지 않는다. Git 작업이 불가능하면 소스 snapshot과 변경 목록을 남기며 push·배포는 범위에 따라 판단한다.

### 매일 이어가는 방식

계획의 기준은 저장소의 `docs/product.md`, `docs/plans/`, `docs/progress.md`, `docs/metrics/`, `docs/learning/`이다. ChatGPT와 Codex가 파일을 자동 공유한다고 가정하지 않는다. 실제 경로·로그·diff가 대화의 추측보다 우선한다.

다음 날 사용할 짧은 요청:

```text
docs/product.md, docs/plans/day-01.md, docs/progress.md와 최신 측정·학습 기록을 읽어줘.
지난 작업의 미완료부터 확인하고 오늘은 2일차 목표만 진행해줘.
오늘 구현 범위·완료 기준·배울 개념을 먼저 짧게 설명한 뒤 작업해줘.
구현·검증·실측·학습 기록을 갱신하고 미확인 사항은 구분해서 보고해줘.
```

종료 보고에는 오늘 목표, 완료 기능, 실제 변경 경로, 실행 명령·결과, 측정 환경·원본·요약, 수동 확인 순서, 미확인·남은 오류, 다음 시작점을 포함한다. 오늘은 여기서 멈춘다.

## 7. 오늘 학습 내용

Codex는 각 작업 전에 관련 개념을 2~3문장으로 설명하고, 완료 뒤 실제 파일·함수와 연결한다. 사용자가 한 번에 전체 코드를 이해해야 다음 단계로 갈 수 있도록 만들지 말고, 작은 기능 단위로 진행한다. 아래 답변은 설계 이해용이며 이력서에서는 구현·검증한 범위로만 말한다.

| Bridge | 서로 다른 실행 환경 사이의 메시지 통신 계약 | WEB_READY·PING·PONG |
| Handshake | 양쪽 통신 준비를 확인하는 절차 | 수신 등록 후 WEB_READY |
| Runtime validation | 실행 중 외부 입력의 실제 형태를 검사 | 메시지 Zod 검증 |
| tRPC | TypeScript 타입을 공유하는 API 구성 방식 | health.check의 서버·클라이언트 타입 |
| Origin | scheme·host·port의 조합 | 허용 웹뷰 주소 검사 |
| RTT | 요청이 갔다가 응답이 돌아오는 왕복 시간 | RN에서 측정한 PING/PONG 시간 |
| Monotonic clock | 시스템 시각 조정에 영향을 받지 않는 경과 시간용 시계 | performance.now 기반 duration |
| Lifecycle cleanup | 화면 종료 시 타이머·리스너·참조를 정리 | unmount·재로드·닫기 |
| Acceptance Criteria | 작업을 완료했다고 판정할 확인 기준 | AC01~AC18의 예/아니오 |
| Baseline | 변경 전 비교 기준이 되는 실제 측정 결과 | 오늘 브릿지 원본과 빌드 환경 |

### 오늘 기능을 설명하는 순서

1. RN 앱과 Next.js 웹은 다른 JavaScript 실행 환경이므로 일반 React props를 직접 공유하지 않는다.
2. 앱은 지정한 Next.js URL을 웹뷰에 로드한다. 웹의 메시지 수신 등록이 끝나면 WEB_READY를 보낸다.
3. 앱은 준비 상태에서 requestId를 붙여 PING을 보내고, 웹은 같은 ID의 PONG을 응답한다.
4. 앱은 메시지의 형태와 ID를 확인하고 자신이 시작한 시계로 왕복 시간을 계산한다.
5. 화면을 닫거나 재로드하면 이전 요청·타이머를 정리한다. 준비되지 않은 새 세션에 이전 응답을 섞지 않는다.
6. health.check 통신은 앱↔서버 HTTP 경로이고, PING/PONG은 앱↔웹뷰 메시지 경로다. 둘을 같은 성능 지표로 해석하지 않는다.
7. 오늘 한도는 고정 fixture다. 실제 로그인·서버 권한·신청 저장·한도 차감은 아직 연결되지 않았다.

### 면접 예상 질문과 답변

**Q1. 기존 React 웹 개발과 React Native에서 가장 달랐던 점은 무엇인가요?**

A. React의 컴포넌트·상태 개념은 활용하지만 DOM·CSS 대신 네이티브 컴포넌트와 플랫폼의 레이아웃·내비게이션을 다뤘습니다. Safe Area, 기기 주소, 앱 빌드와 웹뷰 실행 환경을 별도로 확인해야 했습니다. 실제 구현 후 자신이 확인한 차이를 예로 덧붙입니다.

**Q2. 왜 네이티브와 웹뷰를 함께 사용했나요?**

A. 앱의 이동·홈·사진 기능은 네이티브에 두고 회사별로 달라지는 신청 폼은 웹에서 관리하려는 설계입니다. 대신 준비 상태·인증·메시지·오류 처리가 필요하므로 경계를 명시하고 구현 단계별로 검증합니다. 오늘은 연결 기반까지만 구현합니다.

**Q3. 웹뷰를 띄운 것과 브릿지를 구현한 것은 어떻게 다른가요?**

A. 웹뷰를 띄우면 웹 화면을 볼 수 있지만, 브릿지는 앱과 웹이 요청·결과를 주고받는 계약입니다. WEB_READY로 수신 준비를 확인하고 requestId로 PING/PONG을 대응시키는 동작을 검증합니다.

**Q4. TypeScript를 쓰는데 Zod 검증이 필요한 이유는 무엇인가요?**

A. TypeScript 타입은 실행 중 외부 JSON의 실제 값을 보장하지 않습니다. 브릿지 수신값은 unknown으로 받고 런타임 스키마를 통과한 메시지만 처리합니다. tRPC의 타입 공유도 사용자 입력 검증·인증·권한 확인을 대신하지 않습니다.

**Q5. requestId가 왜 필요하나요?**

A. 여러 메시지와 지연 응답 중 어떤 요청의 결과인지 구별하기 위해 사용합니다. 일치하는 진행 중 요청만 완료하고, 중복 PONG이나 시간 초과 뒤 응답으로 성공 수가 늘지 않게 합니다. requestId 자체는 보안 자격 증명이 아닙니다.

**Q6. 브릿지 성능은 어떻게 측정했나요?**

A. 실제 실행한 경우에만, 같은 RN 시계로 전송 직전과 대응 응답 직후를 측정했다고 설명합니다. 기기·OS·빌드·웹 모드·표본 수·실패를 원본에 남기고 중앙값과 범위를 보고합니다. 이 값은 네트워크 API 시간이나 전체 폼 준비 시간과 구분합니다.

**Q7. 웹 시간과 앱 시간을 빼면 안 되나요?**

A. 서로 다른 실행 환경의 단조 증가 시계는 기준점이 같다고 보장할 수 없습니다. 전체 왕복은 RN 한 환경에서 측정하고, 웹 내부 처리 시간은 웹 자체 구간으로 따로 측정합니다.

**Q8. 왜 Expo Go 대신 Development Build를 준비하나요?**

A. 구글 로그인처럼 프로젝트에 필요한 네이티브 연동을 포함하는 개발 환경을 만들기 위해서입니다. 실제로 어떤 라이브러리와 설정을 포함해 빌드했는지 기록하고, Development Build를 출시 빌드라고 표현하지 않습니다.

**Q9. 메모리 누수나 중복 이벤트는 어떻게 방지하나요?**

A. 화면이 닫히거나 재로드될 때 타이머·진행 중 요청·리스너를 정리합니다. 테스트에서는 종료 뒤 응답, 같은 응답 두 번, 재진입을 확인하고 이전 세션이 새 측정 결과에 영향을 주지 않는지 봅니다.

**Q10. 오늘 작업의 한계와 다음 단계는 무엇인가요?**

A. 오늘은 시안에 맞는 네이티브 화면, 실제 서버 연결과 브릿지 기준선입니다. 아직 실제 인증·DB 신청 저장·한도 처리는 없으므로 2일차에 구글 인증과 서버 사용자·세션을 연결하고 이후 서버 중심의 신청 규칙을 구현합니다.
